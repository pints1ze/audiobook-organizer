## Where things stand
- **Locally:** the API runs on port 5070 and the React client on 5173 (`scripts/start.ps1`, default `both`) with SQLite at `<repo>/data/audiobooks.db`. The client shows the API and database status.
- **Docker:** `docker compose up --build` serves both on port 8080, with `/data`, `/incoming` and `/library` mounted from `./docker/` by default. `docker build --target test .` runs the backend suite on Linux (Ubuntu 24.04) with the runtime's ffmpeg 6.1.1; all 384 pass (slice 64). Add `--no-cache-filter test` to force a rerun. `docs/DEPLOY.md` and `.env.example` document the home-server setup (slice 70).
- **Tag safety:** proven by tests. MP3 writes go through TagLibSharp; M4B writes go through an ffmpeg `-c copy` remux without `chpl`, then TagLibSharp. Chapters and audio survive both. `ChapterReader` reads chapters from both formats. The image ships ffmpeg/ffprobe 6.1.
- **Settings API:** `GET`/`PUT /api/settings` stores the validated incoming and library paths and the keep-source toggle in SQLite (`ApplicationSetting`). The Settings page (`/settings`) edits them, inside a layout with nav, a skip link and a not-found page.
- **Scan inventory:** `ScanService` records every MP3 and M4B under incoming in `AudioFile`, with a `ScanRun` per scan. It skips unchanged files and records unreadable ones, retrying them on the next scan. `POST /api/scans` runs one background scan at a time, `GET /api/scans/latest` shows progress, and `GET /api/dashboard` returns the paths and counts. The dashboard shows the directories, last scan and counts, with a "Scan incoming" button and live progress. The whole flow is verified on Windows dev and in Docker (Linux).
- **Grouping engine:** the pure `GroupingEngine.Group` proposes book groups from scanned file facts, with confidence, evidence and an estimated title and author; scenarios A–E pass. Every completed scan regroups the files it saw into `FileGroup` and `FileGroupFile` (replacing all groups), and `GET /api/groups` lists the groups (least confident first) and the unresolved files. The Incoming page (`/incoming`) shows them with confidence and evidence.
- **Corrections:** `PUT /api/groups/{id}` sets a group's title and author and marks it `UserCorrected`. Rescans keep corrected groups and their files untouched and regroup only the rest. The Incoming page edits title and author in place and marks corrected books "Edited" (slice 14). `GET /api/groups/{id}` lists a group's files in order and `PUT /api/groups/{id}/order` reorders them (slice 15). Each Incoming row has a "Files" disclosure with keyboard-accessible Move up and Move down (slice 16). `POST /api/groups/{id}/files` moves files into a group and `POST /api/groups` creates a group from files; together they give move, merge and split (slice 17). Each Files list has checkboxes and a "Move selected to" bar that moves files to another book or a new book (slice 18). The Unresolved section has the same selection and move bar (slice 19, shared `MoveBar`). `POST /api/groups/excluded` and `POST /api/groups/unresolved` set a file's `UserState`, and `GET /api/groups` lists `excluded` (slice 20). The move bar also offers "Unresolved files" and "Excluded files", and an Excluded section sends files back (slice 21).
- **Metadata search:** `GET /api/metadata/search?keywords=` searches Audible's catalog through `AudibleClient`, a typed `HttpClient` behind `IMetadataProvider`. It returns normalized candidates (ASIN, title, authors, narrators, series, publisher, release date, language, runtime, format, cover URL) (slice 27). `MetadataSearchService` falls back to `OpenLibraryClient` when Audible fails or finds nothing; ISBN keywords search Open Library by ISBN. The response is `{ candidates, providerErrors }`: 400 for blank keywords, 502 only when every provider failed (slice 28). Tests use real responses in `docs/fixtures/audible/` and `docs/fixtures/openlibrary/` through `FakeHttpMessageHandler`. Each Incoming book links ("Find metadata") to `/books/:groupId`, which shows the book and a catalog search prefilled with its title and author, listing candidates and provider errors (slice 29). `PUT /api/groups/{id}/match` stores a picked candidate as the book's `Audiobook` + `MetadataMatch` (one current match, raw candidate JSON) and marks the group `UserCorrected`; `GET` returns it or 204 (slice 30). The book page shows the chosen match and a "Use this match" button on each result (slice 31). Each book stores metadata values in `AudiobookField` with an origin (`file`, `provider`, `user`): `GET`/`PUT /api/groups/{id}/metadata` read them and save user edits, and picking a match copies the candidate in. User values are never overwritten, a gap in the candidate keeps the old value, and Open Library never replaces Audible (slice 32). The book page's Metadata section shows each value with its origin and a "Match: …" line where the chosen match differs, and edits save only the changed fields (slice 33). `GET /api/groups/{id}/cover` lists the files with embedded covers and the chosen cover, `GET .../files/{fileId}/cover` serves an embedded JPEG or PNG, `PUT .../cover` with `{ source: "embedded", fileId }` stores it in `AudiobookCover`, and `GET .../cover/image` serves the chosen one (slice 34). `PUT .../cover` with `{ source: "provider" }` downloads the stored match's cover through `CoverDownloadClient` (https on `m.media-amazon.com` or `covers.openlibrary.org` only, type from the bytes, 502 on a failed download) (slice 35). `PUT .../cover/upload` stores an uploaded JPEG or PNG (multipart `file`, at most 10 MB, typed by its bytes), and `services/api.ts` has typed calls for all cover endpoints (slice 36). The book page's Cover section shows the chosen cover and chooses an embedded cover, the match's cover or an upload (slice 37).
- **Normalization:** `Person`/`PersonAlias` and `Genre`/`GenreAlias` store canonical people (authors and narrators), genres and their variants. `GET`/`POST /api/people`, `PUT /api/people/{id}` (replaces name and aliases) and `GET /api/people/resolve?name=` list, create, edit and resolve people by `NameKey` (whitespace, case and `Last, First` folded); a key owned by another person is a 400 (slice 38). `/api/genres` does the same for genres with `GenreKey` (`-`, `_`, `/` folded to spaces). Both go through `CanonicalNameRepository` and `CanonicalNameService` keyed by `CanonicalKind` (slice 39). `POST /api/{people|genres}/{id}/merge` with `{ fromId }` folds one entry into another: its name and aliases become aliases of the kept one (slice 40). `GET /api/{people|genres}/suggestions` lists likely duplicates (same letters; matching initials for people) with a reason, never merging them (slice 41). The People (`/people`) and Genres (`/genres`) pages list, add and edit entries with their aliases through one `NamesPage` (slice 42), and show possible duplicates and a per-row "Merge into…", each with an inline confirmation (slice 43). `GET /api/groups/{id}/people` resolves each of a book's authors and narrators to a person through the aliases on every read, or lists suggested people for unresolved names; nothing is stored (slice 46). The book page's People section shows each name as normalized or not linked, links it to a suggested person (adds an alias) or adds it as a new person, and reloads after a picked match or a metadata save (slice 47). Books have a hand-entered `genres` list in the metadata API (user values only; a pick never touches it), and `GET /api/groups/{id}/genres` resolves each genre the same way with same-letters suggestions (slice 48). The Metadata section shows and edits genres, one per line; genre errors say "entries" (slice 49). `NameLinks` (`kind` people or genres) shows the People and Genres link sections on the book page (slice 50).
- **Naming:** `NamingTemplate.Render` (in `Services/Naming/`) renders a template into a sanitized relative path with `Missing` tokens or an `Error`, and `NamingTemplate.ResolveUnder` refuses any path outside the library root (slice 44). `GET`/`PUT /api/settings` also store the directory and file templates (defaults below when unset), validated through `Render`; the Settings page edits them (slice 45). `BookTokens.For` maps a book and each file to the tokens, and `GET /api/groups/{id}/preview` shows each file's source, relative path and destination under the library in book order, with missing tokens and errors; nothing is written (slice 51). `GET /api/preview` does this for every book and flags `duplicate` destinations (ignoring case, across books) and destinations that already `exists`, with counts; the per-book preview carries the same flags (slice 52). The Preview page (`/preview`) shows the counts and every book's files From → To with their problems, and can show only books with problems (slice 53).
- **Processing:** `POST /api/jobs` with `{ groupId }` approves a book whose preview is clean (no errors, missing values, duplicate or existing destinations) into a `Queued` `ProcessingJob`, snapshotting each file's source and destination as `Pending` `ProcessingJobFile` rows, and marks the group `UserCorrected`; 400 with a reason, 404, or 409 when already queued or running. `GET /api/jobs` and `/api/jobs/{id}` read them. A hosted `ProcessingWorker` runs queued jobs one at a time: each file is copied through a `.partial` file and renamed into place, never overwriting; a failure records the reason and removes the job's copies; a job cut off by a restart is failed at startup. Sources are only read (slice 55). `TagWriter` makes each copy a tagged file: MP3 through TagLibSharp, M4B through one ffmpeg `-c copy` remux keeping chapters and other tags. It writes title/album, authors as artists and album artists, genres (canonical names when linked), year, track (the bare position: "1", never "01/39"), disc and the chosen cover; empty values keep the source's (slice 56). Each copy is read back in place (title, first artist, track, cover, chapter count, duration ±1 s); a mismatch deletes it and fails the job. When the whole job verified and keep-source is off, each unchanged source is deleted (`SourceDeleted`); a changed or undeletable source is kept with an `Error` and the job still succeeds (slice 57). Each clean book on the Preview page has an Approve button (`approveBook` in `services/api.ts`) that queues it and focuses a "Queued for processing." status, or shows the refusal (slice 58). The Jobs page (`/jobs`) lists jobs with their errors and file details, polls while any is active, and retries a book's newest failed job by approving it again; tests prove a retry leaves one copy per file (slice 59). A test-only spike shows M4B freeform atoms can be written by a TagLibSharp save followed by splicing the remuxed `chpl` back (candidate A); chapters, audio, cover and tags survive (slice 60). M4B copies are remuxed with `-movflags disable_chpl` (chapters only in the QuickTime chapter track) and tagged by TagLibSharp through the same `ApplyTags` as MP3 (slice 61). Copies also carry the Mp3tag script's book fields (narrators as composer, series, part, movement, content group, album sort, subtitle, language, publisher, format, ISBN, ASIN, release time, Audible URL; `stik`/`pgap` on M4B) as ID3v2 frames and iTunes/freeform atoms (slice 62). M4B copies carry no chapters (`-map_chapters -1`) and their read-back skips the chapter check; MP3 copies keep and check chapters (slice 63). At startup a `Running` job is failed as interrupted and its copies and in-flight `.partial` are removed (`ProcessingService.FailInterruptedJobs`), unless one of its sources was already deleted; sources and `Pending` destinations are never touched (slice 65). Tests prove a rescan after processing (keep-source off or on) keeps the groups, adds nothing unresolved and refuses a second approval; the processed book's re-approval is refused (slice 66). A processed book (any `Succeeded` job) leaves `GET /api/groups`, `GET /api/preview` and the dashboard book counts; its book page still works, and approving it again is a 400 "This book was already processed." (slice 67). When a job deletes sources, their `AudioFile` and `FileGroupFile` rows go and each source folder (and parent) left empty is removed, never the incoming root; job history stays, and a rescan finds nothing missing (slice 68). At startup a `Running` job with a `SourceDeleted` file finishes deleting its remaining unchanged sources (checked against the `AudioFile` row's size and last write time; none when keep-source is on) and ends `Succeeded`; other interrupted jobs fail as before (slice 69).
- **Tests:** both test projects exist and all four checks pass.

- 2026-10-18 (slice 05): Settings are key/value rows in `ApplicationSetting`. The schema is `CREATE TABLE IF NOT EXISTS` in `DatabaseInitializer`, with no migration framework. Validation never writes into incoming.

- 2026-10-18 (slice 08): Only one scan runs at a time (409 otherwise). Runs still `Running` at startup are marked `Failed`. Dashboard counts come from the latest completed run.
- 2026-10-18 (slice 10): Grouping is deterministic and rule-based within one container folder. Confidence is the number of agreeing signals (2+ High, 1 Medium, conflict Low). Untagged root files with no shared stem are unresolved.
- 2026-10-18 (slice 11): Groups are fully replaced after each completed scan (a shortcut until phase 4). SQLite foreign keys are enforced on every connection.
- 2026-10-18 (slice 13): Any user correction marks the whole group `UserCorrected`, which freezes its membership; rescans skip its files. New columns on existing tables are added by a guarded `ALTER TABLE ... ADD COLUMN` in `DatabaseInitializer`.
- 2026-10-18 (slice 17): Merge and split aren't separate endpoints. Merge moves all of B's files into A (B is deleted when empty); split creates a user-made group (`High`, "Grouped by the user") from the chosen files.
- 2026-10-18 (slice 18, developer): An excluded file stays excluded until the user undoes it, survives rescans, and can be sent back to unresolved. Unresolved files stay unresolved across rescans.
- 2026-10-18 (slice 20): The exclude and keep-unresolved states live in `AudioFile.UserState`. The grouping engine skips any file with a state; placing a file in a group clears it, and undoing an exclude sends the file to unresolved.
- 2026-10-18 (developer): Phase 4 is reopened for its leftovers. The grouping-rule tweaks are dropped (no real-collection list). Group ids must stay stable: never reused after a group is deleted. (Done in slice 24: `FileGroup` is `AUTOINCREMENT`, and old databases are rebuilt once at startup.)

- 2026-10-19 (slice 28): Providers are tried in registration order (Audible, then Open Library) and the first non-empty result wins; there's no merging. Open Library candidates leave publisher and language empty because its search data mixes print editions.

- 2026-10-19 (slice 32): Metadata values are one `AudiobookField` row per field (JSON value, origin, provider). In a PUT, `null` means "not sent" and `""`/`[]` is an explicit empty user value. The group title and author are a read-time `file` fallback, never stored.
